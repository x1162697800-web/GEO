---

## 1. sitemap 时区归一（无争议，可立刻做）

### 背景

本轮交叉验证证明 Nile 的 C3 判据有确定性 bug：50 个品牌里 39 个七项全测出，
C3 一致率只有 **51%**（七项最低），19 个「他们判 fail 我判 pass」、**0 个反向**，
而这 19 个的 `lastmod` **全部**带非 UTC 时区偏移：

```
Glow Recipe            2026-08-22T05:22:59-04:00   0天前   123 个商品页
Herbivore Botanicals   2026-08-22T02:27:12-07:00   0天前    54
Rare Beauty            2026-08-22T03:03:00-07:00   0天前   134
```

配合 Adwoa Beauty 那条 `fetch_error`：
`exception: can't compare offset-naive and offset-aware datetimes`——证据闭环。

**对 geolook 的意义**：这是个通用陷阱，不是别人家的事。sitemap 的 `lastmod`
有三种常见写法（带 `Z`、带 `±HH:MM`、纯日期），任何做 sitemap 新鲜度判断的代码
都会踩。geolook 现有的 `crawl.discover_sitemap()` 目前**不解析 `lastmod`**
（只取 `<loc>`），所以还没有这个 bug，但一旦要加新鲜度判断就会遇到。

### 改法

本轮已写好可直接搬的实现（在 `D:\GEO\nile-xval\xval.py` 的 `parse_lastmod()`）：
三种格式都吃下，一律归一成 tz-aware UTC，无法解析返回 `None`（而非当作 0，见 R3）。

### 顺带的能力

有了 `lastmod` 解析，可以给站点体检加一项**站点级**信号：
sitemap 是否长期未更新。这条属于「访问/定向层」，与四层依赖模型自然衔接。

**注意**：这一项本身也要过 R1——「sitemap 陈旧影响被引概率」有实证吗？
如果没有，就按 D3 方案 B 的思路处理：这不是影响力预测，而是
**「你声明的更新时间与实际不符」的一致性问题**，属于技术卫生而非优化建议。

## 2. 电商专属维度（D3 已定）

### 想加的三条

来自 Nile 的判据，geolook 现在缺：

| 维度 | 内容 |
|---|---|
| 变体级活价活库存 | 每个变体有独立价格与可售状态，不是父商品一个价 |
| 运费资格 | 目标国的可发货性、时效、费用条件 |
| 商品标识符 | `gtin` / `gtin8/12/13/14` / `mpn` / `sku` 至少其一 |

对做电商客户的审计确实有实际价值——本轮实测里，40 个品牌的 Product schema
完整率（含标识符）只有 74% 一致区间，标识符缺失是常见失分点。

### ⚠️ R1 冲突（这是本阶段的核心问题）

`references/method.md` 开篇写着：「凡是给用户的建议，都要能追到这里的某一条」。
geolook 六维每条阈值都有公开实证锚定（1,943 词 vs 170 词、数字 +61.6%、
定义 +57.3%、对题性 r=0.432、官网仅占 1.37% 引用）。

**这三条电商维度我没有实证支撑。** 它们来自 Nile，而 Nile 的 9 条判据
本身没有任何公开的效果验证——且其中 C3 已被本轮证明有系统性 bug。

**照抄等于把 geolook 最硬的差异化（实证锚定）换成竞品的拍脑袋判据。不能这么干。**

### 定案：归入四层模型的「理解层门票判据」

选项 A（先找实证）在这个领域太新、可能找不到；选项 C（不做）放弃电商子市场。
定案是 B——但归类框架不是「新开一个分类」，而是**复用你已有的四层依赖模型**。

**关键洞察：四层模型本来就已经区分了「门票」和「杠杆」。**

看访问层和定向层的判据性质——robots 放行、sitemap 存在、canonical 正确、
SPA 空壳。**没有一条是影响力预测**，它们全是资格判据：有了不会更好，没有就出局。
而六维里的长度、结构、抽取块才是杠杆。

| 类型 | 例子 | 依据来源 |
|---|---|---|
| 影响力杠杆 | 「补一个定义块能提升 57.3% 被引概率」 | **需要效果实证** |
| 门票判据 | 「UCP 要求每个 offer 带 availability，你没有」 | **协议 schema 本身就是依据** |

电商三条属于后者：协议要求这个字段，缺了就是不合规，这是**事实判断**，
不需要效果实证。归到**理解层**（「机器读得懂这是什么实体吗」），
与访问/定向层同一性质。

这比新开分类好——复用已有概念、不引入第四种东西，而且 `method.md` 四层模型
那节本来就写着「每层依赖上一层」，门票性质是这个模型的内在逻辑。

### 实施约束

- **不进六维总分**。UI 和报告里与六维分数明确分开呈现
- **措辞必须是合规口径**，不能写成「补上能提升被引概率」
  （那是没有依据的影响力断言）
- **依据要可追**：每条判据在 `method.md` 里注明对应的协议 schema 出处
- 只对识别为电商站的项目启用（有 Product schema / `/products/` 路径特征）
- `audit.json` 的 `layers` 字段里，这些判据归入理解层，
  参与 `blocked_by` 的上下游依赖计算

## 3. 验收标准

### 时区归一

- [ ] 三种 `lastmod` 格式（`Z` / `±HH:MM` / 纯日期）都能正确解析
- [ ] 无法解析时返回「未测」而非 0 或当前时间（R3）
- [ ] 有单元测试覆盖三种格式 + 畸形输入
- [ ] 不改变现有 `discover_sitemap()` 的 URL 收集行为（纯新增字段）

### 电商维度

- [ ] `method.md` 的四层模型那节补上「门票判据 vs 影响力杠杆」的区分说明
- [ ] 每条判据注明对应的协议 schema 出处
- [ ] 归入理解层，参与 `layers` 的 `blocked_by` 依赖计算
- [ ] UI/报告里不与六维分数混算
- [ ] 措辞经过检查：无任何未经实证的影响力断言（R1、R9）

## 4. 与 D4 的关系

D4 已定为**四周后再评估**，所以 P3 的时机现在不定。届时的判据：

- 若转向**代理商/咨询交付**（拿 geolook 接单），P3 提前——
  电商维度直接变成可卖的交付项
- 若维持**开源采纳量**，P3 排在 P1/P2 之后——它服务一个子市场，
  而 P0/P1 服务全部用户

第 1 节的**时区归一不受此影响，可随时做**：它是通用能力（任何做 sitemap
新鲜度判断的代码都会踩这个坑），不属于电商子市场。
