## D1 · MCP server：手写 JSON-RPC 还是引入 SDK

**状态**：✅ 已定 — **手写** · 2026-08-23

### 背景

MCP 底层是 stdio 上的 JSON-RPC 2.0，需实现的面很窄：`initialize` 握手、
`notifications/initialized`、`tools/list`、`tools/call`，可选 `resources/*`。
官方 Python SDK（`mcp`）会连带引入 pydantic、anyio、httpx 等一串传递依赖。

geolook 现在**恰好三个第三方包**（`requests` / `beautifulsoup4` / `lxml`），
这写在 README 依赖徽章和部署章节里，与「无 DB、无账号、纯文件」是同一套定位。

### 选项

| | 手写 stdio JSON-RPC | 引入官方 SDK |
|---|---|---|
| 依赖 | 0 新增，纯标准库 | +1 直接，+若干传递 |
| 工作量 | 中（约 150–250 行含工具 schema） | 低 |
| 规范跟随 | `protocolVersion` 协商要自己跟 | SDK 升级即可 |
| 定位一致性 | 保住「三个依赖」卖点 | **破坏卖点** |
| 客户端兼容风险 | 需在多客户端实测 | 社区已验证 |

### 决策理由

**关键论据：这不是一个新的赌注，而是跟已有架构选择一致的延续。**

geolook 已有先例——dashboard 用标准库 `http.server` 手写，没用 Flask/FastAPI。
「少依赖」这条路你已经付过一次手写的代价，且 87 个测试证明它可维护。
MCP 的协议面比 HTTP 服务器窄得多，`json` + `sys.stdin/stdout` 就够。

**stdio 传输天然贴合现有形态**：MCP 客户端把 server 当子进程启动，
即 `python scripts/mcp_server.py`——与 `geo.py` 的 CLI 模式完全一致，
不引入新的运行方式。

### 已知风险与对冲

**唯一真实的维护面是协议版本协商。** MCP 有 `protocolVersion` 修订
（形如 `2024-11-05`、`2025-03-26`），手写要自己声明版本并处理不匹配。

**保留的反方意见**（记下来以便日后复核）：若 D4 最终选「开源采纳量」，
SDK 能降低「在某个客户端里跑不起来」的概率，而「装了跑不起来」是致命的第一印象。
若 MCP 规范在未来一年频繁破坏性变更，手写的维护成本会反超。

**对冲**：协议层封装在单独模块，规范剧烈变动时可整体替换为 SDK。
`P2-compile-targets.md` 的验收标准已要求**在至少两个 MCP 客户端上实测**。

## D2 · 插件独立模式的边界

**状态**：✅ 已定 — **方案 A + 单向使用纪律** · 2026-08-23

### 背景

插件现在硬绑平台（`host_permissions` 只有 `http://127.0.0.1:8765/*`），
平台不跑就没用，所以它是配件而非获客入口。目标是「不装平台也能得到一个真实结论」。

但 `RULES.md` R2 规定指标只能有一份实现——独立模式一旦开始算指标，
就会长出第二套会漂移的实现。

### 选项

**A. 极简（只到「提到/没提到」）** — 内置默认问题集，逐题记录提到与否，
展示「10 题里 8 题没提到你」，导出为平台可导入的样本文件。
→ 完全不碰指标计算，R2 零风险。

**B. 中等（加引用域名分布）** — 在 A 之上做域名频次统计。
→ 平凡可导，勉强不算「指标」，但已在滑向重算。

**C. 完整（本地算提及率等）** — **违反 R2，不采纳。**

### 决策理由

选 **A**。入口产品的任务是**制造动机**，不是给结论。「8/10 没提到你」
这个事实本身就足够刺痛，算出「提及率 20%」不更刺痛，却要付双实现漂移的代价。

### 采样环境问题的化解（关键）

原顾虑：独立模式用户绝大多数在日常登录态下使用，按 `references/method.md`
第 4 节纪律，`personal` 模式**自动降级 D 级待复核**（它测的是「AI 对你的画像」，
不是「陌生人看到什么」）。那入口产品的核心结论就建立在弱证据上。

**方向性化解了这个问题。** `personal` 模式的偏差是朝着
**「更容易提到你自己」**的方向的——用户搜过自己品牌，AI 有其上下文与记忆，
所以它比陌生人更可能提到该品牌。

由此得出**单向使用纪律**：

| 结论方向 | 是否可用 | 理由 |
|---|---|---|
| 「N/M 没提到你」 | ✅ 可用 | personal 模式下是**保守估计**，真实情况只会更差 |
| 「提及率还不错」 | ❌ 禁止 | personal 模式下完全不能作为好消息 |

这样既保住入口产品的钩子，又不违反证据分级。

### 配套约束

- 结果上明确标注采样环境，引导用户开无痕重跑
  （Windows 用户没有 `sandbox.sh`，见 `P0-windows.md` 第 3 节）
- 导入平台时保持 D 级标记，**不因为「是插件采的」就升级**
- 品牌别名要让用户填，并提示「别名缺失会低估提及」
- 默认问题集的来源仍需定（通用买家意图模板 / 按行业几套）——
  这是实施细节，不阻塞开工

## D3 · 电商维度的归类

**状态**：✅ 已定 — **归入四层模型的「理解层门票判据」** · 2026-08-23

### 背景

Nile 的判据里有 geolook 缺的电商专属项：变体级活价活库存、运费资格、
`gtin`/`mpn`/`sku` 商品标识符。对电商客户的审计有实际价值。

但 `RULES.md` R1 要求每条建议能追到实证数据，而这三条**没有实证支撑**——
它们来自 Nile，而 Nile 的 9 条判据本身没有公开的效果验证，
其中 C3 已被本轮交叉验证证明有系统性 bug。

### 选项

**A. 找实证锚定后再做** — 最符合 R1，但领域太新，可能找不到。

**B. 标成另一类判断** — 不进六维评分，作为准入检查呈现。

**C. 不做** — 放弃电商客户这个子市场的差异化。

### 决策理由

选 **B**，但归类框架比初版更贴合已有架构：
**不新开一个分类，而是归入四层依赖模型的「理解层」门票判据。**

**关键洞察：四层模型本来就已经区分了「门票」和「杠杆」。**

看访问层和定向层的判据性质——robots 放行、sitemap 存在、canonical 正确、
SPA 空壳。没有一条是「影响力预测」，它们全是**资格判据**：有了不会更好，
没有就出局。而六维里的长度、结构、抽取块才是杠杆。

| 类型 | 例子 | 依据来源 |
|---|---|---|
| 影响力杠杆 | 「补一个定义块能提升 57.3% 被引概率」 | **需要效果实证** |
| 门票判据 | 「UCP 要求每个 offer 带 availability，你没有」 | **协议 schema 本身就是依据** |

电商三条属于后者：协议要求这个字段，缺了就是不合规，这是事实判断，
不需要效果实证。归到理解层，和访问/定向层同一性质。

这比「新开一个独立分类」好——复用已有概念，不引入第四种东西，
而且 `method.md` 四层模型那节本来就写着「每层依赖上一层」，门票性质是其内在逻辑。

### 实施约束

- **不进六维总分**，UI 与报告里与六维分数分开呈现
- **措辞必须是合规口径**，不能写成「补上能提升被引概率」（无依据的影响力断言）
- 每条判据在 `method.md` 里注明对应的协议 schema 出处
- 只对识别为电商站的项目启用（有 Product schema / `/products/` 路径特征）

## D4 · 阶段目标：采纳量 / 代理商交付 / 可收费产品

**状态**：✅ 已定 — **不阻塞当前阶段，四周后再定** · 2026-08-23

### 背景

原先把它当阻塞项列出，这个判断不准确。

### 决策理由

**前三个阶段同时服务两个方向：**

| 阶段 | 服务开源采纳量 | 服务代理商交付 |
|---|---|---|
| P0 Windows | ✓ 装得上 | ✓ 代理商桌面多是 Windows |
| P1a 商店材料 | ✓ | ✓ |
| P2a 品牌 SKILL.md | ✓ | ✓ 可作交付物 |

D4 真正咬到的只是 **P3 与 P4 的先后**，而那至少在四周之后。

### 一个有用的观察：现有投入已经在回答这个问题

- **采纳量基建**：ProductHunt 上线、geolook.cc、三语 README、演示视频、截图集
- **交付基建**：客户交付包（诊断报告 / 策略 / 执行方案 / 工单 CSV，
  README 明写「为代理商和咨询顾问而建」）
- **计费/许可基建**：**完全没有**

所以真实选项其实是两个而非三个，且这两个不冲突——**代理商是采纳者的一个子集**。

第三个选项（可收费产品）是商业模式问题：geolook 的全部差异化建立在
「数据全在你自己机器上、免费开源、`git init` 就是备份」上。转向收费要么走双许可
（开源核心 + 商业授权），要么走托管版，而后者会直接砸掉「数据主权」这个卖点。
**这不该由代码进度倒推。**

### 四周后重新评估时看什么

- P1a 商店审核是否顺利通过（影响插件作为获客入口的可行性）
- P0 之后有没有出现 Windows 用户的真实反馈（验证漏斗假设）
- 有没有真实的代理商付费/接单需求出现（验证交付方向）
