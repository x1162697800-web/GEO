## 2. 选下一步的规则

按这个顺序挑，不要凭「想做哪块」跳：

1. **正在挡本人开发的**（P0 已过；新的同级阻塞同样插到最前）
2. **外部长杆**（P1a 商店审核）——技术没依赖，但日历在走
3. **修漏斗**（P1b：不装平台也能得到一个真实结论）
4. **低风险纯新增、且已独立**（P2 已过；P3 时区归一属于这一类）
5. **旁路增强**（P3 电商门票）——不挡 1–4
6. **灌流量**（P4）——必须 P1 完成后

**排序逻辑不变：先修漏斗，再灌水。** P4 会带来注意力，注意力落到安装漏斗上；P1 不完成，研究流量是白灌。

**不要在本轮阶段里夹带**第一轮内部重构：判据抽成 `criteria.json`、core/io/store/app 分层、健康分按期固化、delta 噪声门槛。那些仍然有价值，但不是当前执行主线；要做必须先在 `DECISIONS.md` 立新编号，不能趁 P1/P3 顺手改架构。

## 3. 单次改动的开工清单

动手写代码前，按顺序做完。做不到第 4 条就停，去立决策，不要边写边选。

1. 通读 [`RULES.md`](RULES.md)
2. 打开对应 `Px-*.md`（跨阶段的小修复：写明触及哪些 R 条，默认按「需观察」执行）
3. 对照 [`DECISIONS.md`](DECISIONS.md)：这次改动有没有重新打开 D1–D4？有 → 停
4. 写下本次适用的红线（例如 P1b → R2、R9、D2；P3 电商 → R1、R3）
5. 按 R6 定风险等级，并按第 4 节执行对应动作
6. **高风险**：先打一个干净 commit 作回滚基线，再改

## 4. 风险等级对应的动作

优先级说「多重要」，风险说「动手时多小心」。两者独立（R6）。P0 已经示范过：最高优先级也可以是高风险改造。

| 等级 | 典型 | 执行动作 |
|---|---|---|
| **低风险** | 纯新增模块/资产，不改已有逻辑（P2a、P3 时区归一） | 改完跑相关测试即可；随时可撤 |
| **需观察** | 改已有逻辑或已有页面（P1b、P3 电商进 `audit`/`ui`） | **不改公开接口语义**；改完立刻全量测试 |
| **高风险** | 锁、进程管理、发布流程、渲染架构 | 改前基线 commit；小批量；文档里写回滚；**改完声称支持的每个平台都要实测**，测不到的平台必须在文档里写成未验证（R8） |

Windows 上已测、POSIX 未测时：可以写「Windows 已实测」，**不可以**把徽章或 README 写成「全平台已验证」。P0 留下的 POSIX 缺口按这个口径处理。

## 5. 做到什么算完（阶段门禁）

一个阶段只有同时满足下面全部，才能在 `README.md` 第 4 节标成已完成：

1. 对应 `Px-*.md` 的验收清单勾完（或明确注明「未做项 + 理由」，不得默默删掉）
2. `python -m pytest tests -q` 全过；新增能力有对应用例（参照已有 llms.txt / JSON-LD / MCP 测试写法）
3. 声明与实现一致（R8）：README / SKILL.md / UI 文案不超出实测范围
4. 没新增未决策的第三方依赖（R7）；有依赖变化必须先有 D 编号
5. `README.md` 第 4 节状态表已更新，并补「本阶段执行中新发现并修掉的」一条（有则写，无则写无）

**未完成的阶段禁止在对外材料里当已交付宣传。**

部分完成可以写进 README（例如 P0：Windows 完成、POSIX 回归未跑），但必须把缺口单列，不能只留一句「已完成」。

## 8. 执行中撞到计划外缺陷

P0 期间已经发生过两次：`os.kill(pid, 0)` 在 Windows 上杀进程、端口被占时静默绑定。处理规则：

| 情况 | 做法 |
|---|---|
| 就在当前正在改的文件里，**不修会带着更差状态上线**（只改 `killpg` 不改探活，会变成「能停但会被随机杀掉」） | **并进当前阶段**，补测试，写入 README「执行中新发现」 |
| 同文件、同风险等级，但是独立缺陷 | 并进当前阶段，或单独 commit，仍算本阶段范围 |
| 别的模块、不挡当前验收 | **不顺手重构**。记到本文第 7 节或新开 Px 备忘，按第 2 节排队 |
| 需要在 D1–D4 里改选项 | 停工，先写 `DECISIONS.md` 新编号，再动手 |

发现「测不到却被当成 0 / 失败」一律按 R3 修，不论它属于哪一阶段。

发现「429 被当成 WAF 封禁」一律按 R4 修，不许重新合并状态码。

## 9. 新决策怎么立

D1–D4 已定，执行阶段默认遵守，不在 PR 或对话里重开。

只有出现下面情况才追加 `D5` 起的新条目：

- 两个都合理的实现，选错会破坏 R1–R9 或三条腿分工
- 要新增第三方依赖（R7 强制）
- 要改变插件独立模式边界、MCP 传输方式、电商维度是否进六维
- 四周评估到期，需要定 P3/P4 先后（这是 D4 自己规定的复核点）

格式与现有条目一致：**背景 / 选项 / 取舍 / 结论**，不删旧选项。没有新编号就视为「按已有决策做」，不许用代码注释代替决策记录。

详细验收仍以各 `Px` 文档为准。这里只列**一动手就会破框架**的点，避免做着做着滑回旧形态。

| 阶段 | 必须守住 |
|---|---|
| **P1a** | 隐私政策、数据用途声明与真实行为一致（R8）。商店版建议关掉自动跑队列 |
| **P1b** | 独立模式只产出样本 + 提到/没提到；UI **代码层面**不能展示正向提及率（D2）；导入平台后 `personal` 仍是 D 级，不因为「插件采的」就升级；不在插件里做体检、不算指标、不建云端后端 |
